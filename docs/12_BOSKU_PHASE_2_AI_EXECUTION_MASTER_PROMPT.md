# 9. VISIT CONTRACT

A visit may be:

- walk-in;
- linked to a customer;
- anonymous/walk-in without customer identity;
- associated with a capster;
- associated with a service summary;
- completed without a booking.

Statuses:

- expected
- arrived
- in_service
- completed
- cancelled
- no_show

Rules:

- walk-in may start at `arrived`;
- booking may start at `expected`/confirmed state and then become `arrived`;
- completion must not imply payment unless authoritative transaction data says so;
- actual revenue must not be fabricated from visit/service price;
- customer `last_visit_at` updates only for meaningful completed/active visit states according to existing implementation;
- audit meaningful state changes.

# 11. BOOKING MODEL

Booking is optional.

Minimum fields:

- customer;
- date;
- time/slot;
- capster preference where applicable;
- service;
- party size / multiple people where the existing schema permits;
- status;
- projected value.

Lifecycle:

**Confirmed/Expected → Arrived → In Service → Completed**

Alternative terminal paths:

**Confirmed/Expected → Cancelled**

**Confirmed/Expected → No-show**

Do not require every customer to book.

Do not block walk-ins because booking exists.

Do not create actual revenue from projected booking value.

---

# 12. PROJECTED VS ACTUAL

This distinction is mandatory.

### Projected

Can be derived from:

- configured service price;
- eligible booking/service selection;
- documented projection rules.

### Actual

Comes from:

- authoritative Kasir Pro transaction data;
- or later imported transaction snapshots.

Phase 2 must never present a service price estimate as actual revenue.

If no authoritative transaction exists, show:

- projected value;
- actual value unavailable/not synced.

Never invent a payment.

# 21. ACCEPTANCE SCENARIOS FOR PHASE 2

The following must work:

## A — New walk-in

Open Today → create walk-in → optionally identify customer → select service/capster → mark arrived/in service/completed → visit appears in history.

## B — Returning customer

Search customer → open history → start new visit → complete → history updates.

## C — Booking

Create booking → Confirmed/Expected → Arrived → In Service → Completed.

## D — Cancellation

Booking → Cancelled → no completed visit/revenue implication.

## E — No-show

Booking → No-show → no actual revenue.

## F — Walk-in remains independent

A walk-in must not require a booking record.

## G — Capster

Owner creates/activates capster → operational user can select active capster → visit records attribution.

## H — Service

Owner creates/activates service → operational user can select it → configured price may contribute to projection only.

## I — Projection

Booking/service has configured price → projected value visible → actual remains separate/unavailable until authoritative transaction data exists.

## J — Permission

Operator attempts owner-only capster/service configuration mutation → server rejects.

## K — Identity safety

Two customers with same name are not silently merged.

## L — No secret dependency

Fresh development setup does not require a user-provided bootstrap/API token for Phase 2.
